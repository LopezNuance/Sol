## 2. Gap analysis: what formal submission requires

1. **A stable, non-draft version.** "v0.1.0-draft, frozen" cannot be submitted as-is; the Change Control section requires unfreeze + version bump for any normative change, and the 11 blocking open questions are normative-relevant.
2. **Published normative artifacts.** Appendix C requires published schemas for 10 artifact classes; §59 Q11 requires the machine summary schema as a normative artifact. Only schema-light drafts exist.
3. **A physical container.** The MVP (§57 item 1) requires the `.solnb` container; only the non-normative exploded debug representation exists.
4. **Validating examples.** Change Control gate: "Complete examples intended for conformance use must validate." GOLD-01 has not been assembled from the spec examples, and the freeze review flagged a duplicate example digest that breaks that gate.
5. **MVP surface beyond the validator.** Executor, safe HTML/Markdown rendering, and `.ipynb` import are in MVP scope but unimplemented.
6. **Acceptance demonstration.** The 25 acceptance criteria (§58) need a recorded demonstration, not just a passing pathology corpus.
7. **Namespace clearance.** Name, extension, and media type are explicitly pending review; a media type of the form `application/vnd.sol.notebook` implies an IANA registration if this is a public standard.
8. **External review.** A formal submission needs a review/comment cycle on the promoted version, with findings triaged (errata / corpus entry / unfreeze candidate) per the freeze review's discipline.
9. **Reproducible companion evidence.** The QRY freeze gate evidence is not reproducible from this repo (see state table).

## 3. Next steps

### Phase 0 — Decide the submission venue (decision, ~1 session)

- Determine what "formal submission" means: IETF-style RFC, an internal standards process, or public specification publication.
- Record the venue's requirements (versioning policy, review process, schema publication channel, media-type registration, trademark review) as a checklist in the repo.
- This gates the target version number and the depth of the external review in Phase 5.

### Phase 1 — Resolve the 11 v0.1-blocking open questions by implementation (§59)

The freeze review assigned each question a resolution path; execute them:

1. **Physical container (Q1):** benchmark candidate containers (e.g., ZIP-based, tar-based, OCI layout) against REQ-014.1–REQ-014.5 (bounded manifest read, structural index, random object access, integrity, progressive loading); record the decision and rationale.
2. **Minimum environment manifest (Q2):** define the minimum set of environment fields a run record must carry for provenance (acceptance criterion 11).
3. **Mandatory compression codecs (Q3):** fix the codec list (MVP item 30 requires lossless compression).
4. **Branch support minimum (Q4):** fix the v0.1 branch floor (MVP item 8 requires at least one branch).
5. **Minimum object-size support (Q5):** set the minimum object size a conforming store must handle.
6. **Imported `.ipynb` output classification (Q6):** define how imported outputs are classified (acceptance criterion 15).
7. **Cell-summary strictness (Q7):** resolve via the published cell schema (Phase 2).
8. **Mandatory actor fields for agent-authored commits (Q8):** resolve via the published actor schema (Phase 2).
9. **Minimal claim/evidence schema (Q9):** resolve via the published record schemas (Phase 2).
10. **Mandatory semantic-record status fields (Q10):** resolve against the status model (§20) and record schemas (Phase 2).
11. **Machine summary schema (Q11):** publish `machine_summary.schema.json` as a normative artifact (Phase 2).

Each resolved question gets a dated decision note in the repo (errata if wording-only, version bump if normative).
